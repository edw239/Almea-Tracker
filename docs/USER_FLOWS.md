## 0. Вход: зафиксированная бизнес-модель

| Вопрос | Ответ | Следствие для продукта |
| ------ | ----- | ---------------------- |
| Модель | Внутренний инструмент Almea; через ~год — продажа похожим производственным компаниям | Тенант сейчас не вводим, но убираем швы, которые потом дороги (§11) |
| Первичная персона | Владелец / CEO: «не вижу, что происходит и что горит» | Главный экран владельца — не список задач, а «что горит» (F5) |
| Что заменяем | Excel / Sheets, действующий трекер, частично 1С / ERP | Нужен импорт (F10); причина ухода с прежнего трекера задаёт главную ставку (§1.2) |
| Команда | До 10 человек, почти все за компьютером | Web-first достаточно; мобильное приложение и бот — не в v1 |
| Успех через 3 месяца | 0 потерянных поручений: исполнитель + срок у каждой задачи | Метрика становится **инвариантом ввода**, а не отчётом (F2, §8) |
| Ритм | Ежедневный: утреннее «что у меня сегодня» + стендап | Дневной цикл приоритетнее недельного; регулярка нужна (F6) |

Открытые продуктовые вопросы закрыты 18.08.2026; решения разнесены по разделам, сводка — §12.

### 0.1. Главный риск этой конфигурации

Владелец — первичная персона, но он **читатель**, а не основной автор данных: данные создают 5–9 исполнителей. Отсюда классический провал внедрения:

```
Владельцу трекер нравится → исполнители не заходят → картина устаревает
    → владелец принимает решения по неверным данным → возвращается в чат и Excel
```

Поэтому флоу исполнителя (F3, F4, F7) в этом документе приоритетнее флоу владельца (F5), хотя владелец — первичная персона. Владелец получает ценность только как побочный эффект дисциплины исполнителей, и продукт обязан эту дисциплину делать дешёвой, а не требовать её.

## 1. Позиционирование

### 1.1. Обещание

> Небольшая производственная компания видит все поручения, сроки и блокеры в привязке к брендам, партиям и сделкам — и ни одно поручение не теряется между встречей и цехом.

### 1.2. Почему не прежний трекер — причина зафиксирована

Компания ушла с прежнего трекера потому, что **задачи не были связаны с брендами, партиями и сделками — они висели в воздухе.** Это не претензия к интерфейсу, а структурная проблема: в универсальном трекере контекст приходилось держать в голове или дублировать тегами.

Отсюда четыре продуктовые ставки:

| Следствие | Что делаем |
| --------- | ---------- |
| Host-домен — не побочная фича, а причина существования продукта | Привязка к сущности встроена в **сам ввод** задачи (F2), а не спрятана в дополнительные поля |
| Нужен справочник сущностей, а не свободная строка | `domainEntityId` перестаёт быть строкой из головы: реестр, поиск, защита от дублей (F8) |
| Ценность видна на карточке сущности, а не в списке задач | Карточка бренда / партии / сделки — второй по важности экран после «моего дня» |
| Универсальность — антицель | Каждая абстракция, не привязанная к домену, приближает нас к тому, из чего ушли |

Как проверяем ставку: доля задач с привязкой к сущности ≥ 60 % в операционных списках плюс рост открытий карточек сущностей. Если через месяц привязка не прижилась — ставка неверна и настоящая причина ухода была другой.

### 1.3. Продуктовые non-goals

Дополняют инженерные non-goals из principles §1.3.

| Не делаем в v1 | Почему |
| -------------- | ------ |
| Мобильное приложение, Telegram-бот | Команда за компьютерами; канал ввода не является узким местом |
| Замена 1С / ERP (склад, партии как источник истины) | Трекер — про поручения, не про учёт. Сущности приходят ссылкой (F8) |
| Отчётность для внешних (инвесторы, аудит) | Другой потребитель, другой уровень доверия к данным |
| Соцфункции: лента, реакции, статусы «онлайн» | На 10 человек коммуникацию закрывает комментарий и упоминание |
| Оценка загрузки и планирование мощностей | Требует трудозатрат и учёта времени — явный non-goal ядра |

## 2. Персоны

Персона — режим работы, а не должность: в компании до 10 человек один человек совмещает P1 и P2.

### P1. Владелец (режим «обзор и поручения»)

| Поле | Значение |
| ---- | -------- |
| Контекст | Держит в голове бренды, завод, лабораторию, сделки. Дробный день, много коротких решений |
| Боль | Не видит, что горит; узнаёт о срыве, когда уже сорвано; вынужден опрашивать людей |
| Что делает в продукте | Утренний обзор (F5), поручения (F2), приёмка (F4), недельный разбор (F9) |
| Частота | 5–15 коротких заходов в день |
| «Продукт для него работает», если | На стендапе он не задал ни одного вопроса «а что с…» |
| Как теряется | Экран показывает много задач, но не показывает риск → возвращается к личным звонкам |

### P2. Руководитель направления (режим «мой участок и мои люди»)

| Поле | Значение |
| ---- | -------- |
| Контекст | Лаборатория, производство, маркетинг или продажи. 2–4 подчинённых |
| Боль | Дважды пересказывает контекст: наверх владельцу и вниз исполнителю |
| Что делает в продукте | Поручения своим (F2), приёмка (F4), разбор блокеров (F7), участок в F5 |
| Частота | Ежедневно, 20–40 минут суммарно |
| «Работает», если | Приёмка занимает 5 минут вместо совещания |
| Как теряется | Если приёмки нет, он всё равно перепроверяет вручную — трекер для него бесполезен |

### P3. Исполнитель (режим «мой день»)

| Поле | Значение |
| ---- | -------- |
| Контекст | Технолог, оператор, маркетолог, менеджер. Работает по конкретным задачам |
| Боль | Непонятно, что первое; поручения приходят из чата, встреч и коридора |
| Что делает в продукте | Утро (F3), сдача (F4), блокеры (F7). Почти не создаёт задачи |
| Частота | 2–5 заходов в день, если привычка сложилась |
| «Работает», если | Утром не надо ничего вспоминать и ни у кого спрашивать |
| Как теряется | Пустой или неактуальный экран на первом входе; обновление статуса ощущается как отчётность ради отчётности |

### P4. Ассистента нет — и это меняет требования

Обычно в компании такого размера самый активный пользователь трекера — ассистент, который вводит задачи за руководителем и следит за гигиеной данных. **В Almea такого человека нет: владелец вводит задачи сам.** Три следствия, которые дороже любого экрана:

| Следствие | Требование |
| --------- | ---------- |
| Ввод конкурирует со временем самого дорогого человека в компании | Поручение создаётся за 5–10 секунд в одном ряду, без модального окна и переходов (F2) |
| Разбор «Входящих» никто не сделает за владельца | Задача без исполнителя — не тишина, а первый блок его же утреннего обзора (F5) |
| Гигиену данных не поддержит человек | Её поддерживают ограничения ввода и агрегаты, а не регламент |

Если ввод поручения окажется дороже, чем написать в чат, владелец вернётся в чат — и это главный сценарий провала продукта.

## 5. Флоу

### F0. Запуск в компании

| Поле | Значение |
| ---- | -------- |
| Персона | Владелец + администратор |
| Триггер | Решение перейти с Excel и прежнего трекера |
| Вход | Сид базы, `#/login` |
| Критерий выхода | Каждый сотрудник вошёл хотя бы раз и видит минимум одну свою задачу |
| Метрика | Время от старта до «вошли все» — цель ≤ 3 рабочих дня |

Шаги: сид → Spaces по направлениям (лаборатория, производство, маркетинг, продажи) → заведение людей и ролей → импорт живых задач (F10) → объявленное правило «поручение существует, только если оно в трекере».

| Путь отказа | Сегодня | Должно быть |
| ----------- | ------- | ----------- |
| Людей невозможно завести | **закрыто:** `#/people`, `POST /api/users` | — |
| Задачи переносят руками | нет импорта | CSV-импорт (F10) |

**Состояние: люди есть, импорта нет.** Сотрудника заводит админ; одноразовый пароль показывается один раз.

### F1. Первый вход сотрудника (активация)

| Поле | Значение |
| ---- | -------- |
| Персона | Исполнитель |
| Триггер | Получил доступ |
| Вход | `#/login` → `#/` |
| Критерий выхода | В первую сессию человек **изменил статус** хотя бы одной задачи, а не просто посмотрел |
| Метрика | Activation rate: доля приглашённых, закрывших ≥ 1 задачу за 3 дня. Цель ≥ 80 % |

Шаги: вход → смена пароля → `#/` с 1–3 задачами, назначенными **заранее** → проверка имени и таймзоны в `#/me?tab=profile` → первая задача в работу.

| Путь отказа | Почему критично |
| ----------- | --------------- |
| Пустой My Work на первом входе | «Мне тут нечего делать» — второго входа не будет. Правило: не выдавать доступ, пока человеку не назначены 1–3 реальные задачи |
| Пароль остался выданным администратором | закрыто: `mustChangePassword` + `#/change-password` |

**Состояние: смена пароля обязательна.** Пустой первый экран (нет заранее назначенных задач) всё ещё риск активации.

### F2. Поручение — ключевой флоу вашей метрики

| Поле | Значение |
| ---- | -------- |
| Персона | Владелец, руководитель |
| Триггер | Встреча, звонок, обход цеха, мысль в 23:40 |
| Частота | 10–20 в день на владельца, который вводит сам (ассистента нет) |
| Вход | Ряд быстрого ввода на `#/`, карточка сущности `#/host/:type/:id`, список `#/lists/:id` |
| Критерий выхода | У задачи есть исполнитель **и** срок; желательно привязка к сущности; исполнитель уведомлён |
| Метрика | Доля задач с исполнителем и сроком — цель ≥ 95 %. Медиана времени создания — цель ≤ 10 секунд |

Целевая механика ввода — **один ряд, четыре слота, Enter**: заголовок → исполнитель → срок → сущность (бренд / партия / сделка). Никаких модальных окон и переходов между экранами: ввод конкурирует со временем владельца, и если он дороже сообщения в чат, победит чат.

| Путь отказа | Сегодня | Должно быть |
| ----------- | ------- | ----------- |
| Захватил мысль без исполнителя | задача навсегда остаётся в личных «Входящих» | «Входящие» — очередь разбора; задача без исполнителя старше 24 ч поднимается первым блоком обзора владельца (F5) |
| Исполнитель не понял, что от него хотят | ничего не требуется | поле описания сразу в фокусе после создания, но **не блокирует** — иначе ввод перестаёт укладываться в 10 секунд |
| Срок «когда-нибудь» | `dueDate` опционален всегда | «без срока» допустимо только для личных задач (owner = assignee) |
| Задача не привязана к сущности | привязка недоступна из быстрого ввода | четвёртый слот с поиском по реестру (F8); пропуск разрешён, но попадает в метрику ставки §1.2 |

**Состояние: ряд ввода и due при делегировании есть.** `QuickAdd` — title / assignee / due / brand; API `TASK_DELEGATION_REQUIRES_DUE_DATE`; `scope=untriaged` + счётчик в summary. Описание по-прежнему не в ряду (открывается после создания).

### F3. Утро исполнителя

| Поле | Значение |
| ---- | -------- |
| Персона | Исполнитель |
| Триггер | Начало дня, около 09:00 |
| Вход | `#/` |
| Критерий выхода | Блок «Сегодня» разобран: каждая задача либо в работе, либо перенесена с новым сроком, либо возвращена постановщику |
| Метрика | DAU / WAU исполнителей — цель ≥ 0,7 при ежедневном ритме. Guardrail: доля дней, где просроченные не тронуты |

Шаги: `#/` → бакеты Просрочено / Сегодня / Без срока / Позже (`GET /me/buckets`) → приоритизация → первая задача в работу.

| Путь отказа | Сегодня |
| ----------- | ------- |
| Картина неполная | **закрыто:** сервер считает бакеты в timezone профиля |
| «Сегодня» у разных людей разное | **закрыто:** один источник — API + `summaryDayBounds` |

**Состояние: done.** Скоупы ЛК-1, activity ЛК-3, планировщик П-Ритм. На `#/` группировка — из `GET /me/buckets?scope=` (не клиентский `bucketMyWorkTasks`).

### F4. Сдача и приёмка — замыкание контура

| Поле | Значение |
| ---- | -------- |
| Персона | Исполнитель → постановщик |
| Триггер | Исполнитель закончил работу |
| Вход | Карточка задачи |
| Режим | **Опциональный:** постановщик решает при создании — галочка «нужна приёмка» |
| Критерий выхода | Задачу с приёмкой закрывает постановщик, исполнитель только сдаёт |
| Метрика | Доля задач с приёмкой, принятых в течение 2 рабочих дней; доля возвратов (метрика качества постановки, не работы) |

Шаги: исполнитель ставит «На проверке» → постановщик получает уведомление → принимает (задача уходит в `DONE`) или возвращает с комментарием (снова в работу, срок пересогласован). Без галочки задача закрывается как сейчас — исполнителем.

Почему это критично для вашей метрики: «поручение не потеряно» — это не «создано с исполнителем», а «доведено до подтверждения». Без приёмки владелец не может доверять статусу `DONE` и продолжает переспрашивать, то есть возвращается в чат.

Почему дефолт именно такой: опциональная галочка, выключенная по умолчанию, не включается никогда — в момент постановки владелец экономит секунды, а цена отсутствия приёмки проявляется через неделю, и механизм остаётся мёртвым кодом. Включённый по умолчанию для поручений другому дефолт замыкает контур сам, сохраняя право снять галочку там, где приёмка — формальность.

**Состояние: контур замкнут.** `review_required`, колонка «На проверке», исполнитель не закрывает при приёмке, постановщик принимает/возвращает, `TASK_REVIEW_REQUESTED`, `scope=review`.

Реализация, не ломающая dual status (principles §4): list status «На проверке» с `category = IN_PROGRESS`, поле `review_required` на задаче, уведомление `TASK_REVIEW_REQUESTED`, право закрытия у постановщика при `review_required = true`. Новый canonical enum не нужен — отчёты и автоматизации продолжают читать четыре категории. `created_by_user_id` уже есть.

Дефолт решён: **галочка включена, когда постановщик ≠ исполнитель**, и снимается одним кликом. Для своих задач приёмки нет.

### F5. Обзор владельца и стендап

| Поле | Значение |
| ---- | -------- |
| Персона | Владелец |
| Триггер | Стендап, 10–15 минут |
| Вход | `#/overview` |
| Критерий выхода | Прошёл шесть блоков и не задал ни одного вопроса «а что с…» |
| Метрика | Доля решений стендапа, принятых по экрану, а не по опросу людей; длительность обзора |

Шесть блоков экрана: просрочено по людям → блокеры → нераспределённое (без исполнителя или срока) → **без движения ≥ 3 дней** → ждёт моей приёмки → **переносили срок ≥2 раз**.

| Путь отказа | Почему опасно | Ответ |
| ----------- | ------------- | ----- |
| Блоки пустые, потому что исполнители не обновляют статусы | ложное спокойствие — худший исход для владельца | Блок «без движения» обязателен: он ловит молчание, а не работу |
| Экран показывает все задачи компании | владелец тонет и перестаёт открывать | Никогда не делать «все задачи» первым экраном владельца |

**Состояние: экран владельца есть.** `GET /api/overview` — unassigned / stale (3 раб. дня) / blocked / awaitingReview / rescheduled (`dueDateMoveCount ≥ 2`) / overdueByUser; ACL; `#/overview`; сайдбар считает из `/me/summary`.

### F8. Контекст домена: бренд, партия, сделка, проект — главная ставка продукта

Это тот флоу, отсутствие которого выгнало компанию с прежнего трекера (§1.2). По приоритету он идёт сразу за вводом задач, а не в конце списка.

| Поле | Значение |
| ---- | -------- |
| Персона | Владелец, руководитель |
| Триггер | Обсуждаем XLASH или конкретную партию |
| Вход | Реестр сущностей + карточка `#/host/:entityType/:entityId` |
| Критерий выхода | По любой сущности видно всё связанное, без ручных тегов и без знания её идентификатора |
| Метрика | Доля операционных задач с `domainEntityId` ≥ 60 %; частота открытия карточек; число дублей = 0 |

Решение по источнику данных: **сущности заводятся руками в трекере, нужен справочник с поиском.** Синхронизация с 1С / ERP — отдельная фаза, не в v1.

Что для этого нужно сверх текущего каркаса:

1. Реестр сущностей как таблица (тип, отображаемое имя, признак архива), а не строка `domainEntityId` из головы.
2. Поиск по реестру внутри быстрого ввода (четвёртый слот F2) и создание новой сущности из того же места.
3. Список сущностей по типу — сейчас попасть на карточку можно только прямым адресом.

| Путь отказа | Сегодня |
| ----------- | ------- |
| Опечатка в идентификаторе | `ensure` создаёт список по любому переданному id (в сиде — строка `xlash`) → две карточки одного бренда |
| Нельзя найти сущность | справочника нет, только deep-link по прямому адресу |
| Привязка требует лишних действий | из быстрого ввода привязать нельзя → доля задач с привязкой останется низкой, ставка §1.2 провалится по вине интерфейса, а не идеи |

**Состояние: реестр + привязка из ряда ввода есть.** `#/brands`, `hostEntityId` в QuickAdd и на задаче; в UI только `brand`.

## 7. Метрики

### 7.1. North Star

> **Доля поручений недели, доведённых до приёмки без ручного напоминания.**

Почему не «число задач» и не «число закрытых»: и то и другое растёт от бардака. Формулировка через приёмку и отсутствие напоминания напрямую выражает «ничего не теряется» и не даёт накрутить себя объёмом.

### 7.2. Дерево метрик

| Слой | Метрика | Цель | Где считать |
| ---- | ------- | ---- | ----------- |
| Ввод | задач с исполнителем и сроком | ≥ 95 % | при создании (F2) |
| Ставка §1.2 | задач с привязкой к сущности домена | ≥ 60 % в операционных списках | F2, F8 |
| Дисциплина | активированные исполнители, DAU / WAU | ≥ 0,7 | входы + смены статусов |
| Пропускная способность | доведено до приёмки за неделю; медиана «постановка → приёмка» | тренд вниз по времени | F4 |
| Гигиена (guardrail) | без движения > 3 рабочих дней и без блокера | ≤ 5 % | F5, F7 |
| Гигиена (guardrail) | нераспределённые старше 24 ч | 0 | F2 |
| Антигейминг | доля отмен и переносов | не должна расти вместе с NSM | F9 |

Последняя строка обязательна: без неё NSM легко «улучшить», отменяя и перенося задачи вместо их выполнения.

### 7.3. Как считать

На 10 человек не тащить внешнюю аналитику: `GET /me/summary` (ЛК-3) для личных бакетов + один админский эндпоинт здоровья для §7.2. Считать по базе, а не по событиям фронтенда.

## 8. Инварианты правдивости данных

Продуктовые правила того же уровня жёсткости, что инженерный чеклист principles §16. Они, а не отдельные фичи, обеспечивают метрику «ничего не теряется».

1. Поручение другому человеку не создаётся без исполнителя и срока.
2. Задачу с запрошенной приёмкой закрывает постановщик; исполнитель сдаёт. Приёмка запрашивается по умолчанию, когда постановщик ≠ исполнитель.
3. «Без срока» допустимо только когда владелец задачи и исполнитель — один человек.
4. Задача не стоит без движения больше трёх рабочих дней без блокера или нового срока.
5. Неразобранные «Входящие» старше 24 часов — видимый долг, а не тишина.
6. Перенос срока — с причиной; второй перенос попадает в недельный обзор.
7. Регулярное создаётся расписанием, а не памятью человека.
8. Сущность домена выбирается из реестра, а не вводится строкой: свободный ввод порождает дубли и убивает F8.
9. Один источник правды: если задача только в Excel — её нет.

## 11. Шов под будущий SaaS

Модель «сначала Almea, через год — продажа». Консервативный подход: тенант **не вводить сейчас** (нет второго клиента — это спекуляция), но убрать два шва, которые потом стоят дорого, и записать третий как известное ограничение.

| Шов | Где | Почему дорого потом | Что сделать сейчас |
| --- | --- | ------------------- | ------------------ |
| Глобальный `systemKey` | `schema.prisma:112` — `TaskSpace.systemKey String? @unique` | Второй компании нельзя иметь свой `personal` space: ключ занят. Код ищет space по глобальному ключу (`upsert({ where: { systemKey } })` в сиде) | Не размазывать поиск по глобальному ключу: одна функция `resolveSystemSpace()`. Тогда переход на `@@unique([organizationId, systemKey])` — одна миграция |
| Almea-специфика в коде | `DEFAULT_TIMEZONE = 'Asia/Dubai'`, `HOST_ENTITY_TYPES = brand\|batch\|deal\|project`, русские названия статусов, сид «Стратегия 2030» | Для второй компании это конфигурация, а не код | Держать как «отраслевой профиль» / параметры сида, а не константы модуля |
| Глобальный `User.email @unique` | `schema.prisma:79` | В SaaS один человек может работать в двух компаниях | Не трогать; записать как известное ограничение |

Плюс правило на каждый новый экран: это отчёт **по компании**, а не по Almea — без зашитых названий брендов и направлений.

Не делать сейчас: биллинг, таблицу организаций, саморегистрацию, домены на клиента.

| 5 | Внешние участники | Нет, только сотрудники | ACL не расширяем, роль VIEWER остаётся для внутренних наблюдателей |
| 6 | Канал напоминаний | In-app + браузерное уведомление; email позже | §6.3; планировщик считает по всем пользователям, эскалация — через агрегат руководителя |
| 7 | Ассистент | Нет, владелец вводит сам | §2 P4, требование «ряд ввода за 10 секунд» в F2 |
| 8 | Порог «без движения» | 3 рабочих дня | F5, F7, guardrail §7.2 |
| 9 | Типы сущностей в v1 | Только **бренд / SKU**. `batch`, `deal`, `project` остаются в enum как зарезервированные и **не светятся в UI** | П-Домен; тот же принцип, что с триггерами автоматизаций — не показывать нереализованное |
| 10 | Обязательность привязки к сущности | Не обязательна: задача без привязки просто не попадает в карточку бренда. Давление вместо запрета | F2, F8, метрика ≥ 60 % |

### 12.1. Что осталось решить

| Вопрос | Почему важно | Мой вариант |
| ------ | ------------ | ----------- |
| Кто ведёт реестр брендов | Без ответственного справочник зарастёт дублями и архивными записями | Владелец; создание из ряда ввода, чистка — в недельном обзоре |
